# 新记录的显示编号

平台网页对新记录显示日期流水号，例如 `b261026-001`、`cr261026-001`、`eval261026-001`、`t261026-001`、`tr261026-001`。实际记录 ID、请求编号、目录、下载文件名、表格和校验摘要保持原样。

## 使用方式

- 点击显示编号查看完整编号，旁边按钮复制完整编号，便于在日志和 9011 中定位。
- 列表和下拉框可以搜索显示编号、完整编号及已有名称；实际操作仍提交完整编号。
- 新上传任务优先显示原始文件名。报告标题不再重复显示运行目录和运行编号。
- 历史长编号不补号，历史任务重新打开或预处理仍保留原编号；旧批次中新建的采集、评估运行会得到新的运行显示号。
- 新手工上传批次在正式登记时获得批次和任务显示号；轨迹在正式预处理转换发布后获得显示号，后续质检、修正和 COT 页面沿用。同一用例在不同运行的轨迹不会共用显示号。
- 已经使用原生日期流水号的 Pipeline、处理作业和发布数据集直接显示已有编号。原始用例编号、手机序列号、规则版本及来源轨迹名不改写。训练混合中的纯前端演示任务没有真实后端登记，仍保留其原编号。

## 实现与接口

新增 `POST /api/display-identifiers/resolve`。请求示例：

```json
{"items":[{"kind":"run","id":"eval_完整编号"},{"kind":"trajectory","id":"tr_完整编号","scope":"所属批次完整编号"}]}
```

响应按请求顺序返回 `items`，每项包含 `kind`、`id`、`scope`、`display_id`、`mapped`。接口只读，每次最多 1000 项；没有映射时 `display_id` 为原 ID。只有任务和轨迹使用批次 `scope`。

显示映射保存于现有数据库的 `display_identifiers` 命名空间，新手工批次的登记标记在 `display_identifier_batches`。没有数据库结构迁移。真实短编号和显示别名共用原子计数、分别保留用途；显示别名不会写入 `batch_identities` 或启用短路径布局。编号按北京时间日期和类型分配，序号超过 999 自动扩展，预留后未完成的编号可能留空，不代表任务丢失。

新运行与映射原子保存。新批次和转换结果的映射与正式产物原子提交；失败重试复用预约，避免跨日重试换号。查询不会给历史记录分配编号。

前端共用批量解析缓存，每批最多 200 项。解析失败时显示原 ID，保留业务操作；不会把短显示号作为接口参数。已确认映射在本次页面会话内复用，未映射或暂时失败的结果短暂缓存后可以重查。

## 同步与验收

1. 备份平台数据库和当前代码，通过 GitHub 同步本次平台前后端文件，包括新增模块。
2. 重启平台后端；在 `frontend` 运行 `npm run build` 并更新静态资源（开发环境重启前端服务），刷新浏览器。
3. 用一个新上传请求登记批次，再启动采集或评估；确认看到短号。重复使用旧上传请求或打开旧记录不会补号。
4. 用完整编号和短号分别搜索，检查复制得到完整 ID；同步、取消、预览和下载仍对应同一运行。
5. 完成新批次预处理，核对同一轨迹在预处理、质检和修正页面编号一致。

不需要更新 9011，不重命名历史文件。Windows 实际路径长度没有因网页短号而缩短。回滚时恢复平台代码及前端构建并重启即可；新增映射可保留，旧代码不会读取它们，不需要删除历史数据。
